Object-Oriented Programming

Student Handout
From bundling data and behavior together to how real software is actually structured

1. What is Object-Oriented Programming?

Object-Oriented Programming (OOP) is a way of organizing a program around objects — things that bundle data (attributes) and behavior (methods) together, instead of keeping data and the functions that act on it completely separate.

Easy mental model: OOP = describing a "thing" once (a class), and then creating as many real copies of that thing (objects) as you need — each with its own data, but sharing the same behavior. 
class Dog:
    def __init__(self, name):
        self.name = name

    def bark(self):
        return f"{self.name} says Woof!"

my_dog = Dog("Rex")
print(my_dog.bark())
Output:Rex says Woof!

2. Classes vs Objects

A class is a blueprint — it describes what something will look like and what it can do, but it isn't an actual thing by itself. An object (also called an instance) is a real, concrete thing built from that blueprint.

Everyday example: "Dog" as a concept is a class — it describes ears, a tail, barking. Your actual pet Rex is an object: one specific dog built from that description, with his own name and age. 
class Dog:
    pass

rex = Dog()      # an object (instance) of Dog
buddy = Dog()    # another, completely separate object

print(rex is buddy)  # False — two different objects

You can create as many objects as you want from a single class, and each one is independent of the others.

3. The __init__ Constructor and self

__init__ is a special method that runs automatically whenever a new object is created from a class. It's used to set up the object's initial data.

self refers to the specific object being worked with. Every method inside a class takes self as its first parameter so it knows which object's data to use.

class Student:
    def __init__(self, name, cgpa):
        self.name = name
        self.cgpa = cgpa

ali = Student("Ali", 3.7)
sara = Student("Sara", 3.9)

print(ali.name, ali.cgpa)     # Ali 3.7
print(sara.name, sara.cgpa)   # Sara 3.9
Notice: Even though both objects were built from the same class, self.name and self.cgpa hold completely different values for ali and sara. self is what keeps each object's data separate.

4. Attributes and Methods

An attribute is a piece of data that belongs to an object (a variable stored on self). A method is a function that belongs to a class and describes something the object can do.

class Car:
    def __init__(self, brand, fuel):
        self.brand = brand      # attribute
        self.fuel = fuel        # attribute

    def drive(self):            # method
        if self.fuel > 0:
            self.fuel -= 10
            return f"{self.brand} is driving. Fuel left: {self.fuel}"
        return f"{self.brand} is out of fuel!"

car = Car("Toyota", 50)
print(car.drive())   # Toyota is driving. Fuel left: 40
print(car.drive())   # Toyota is driving. Fuel left: 30

Notice how calling drive() changes the object's own attribute (self.fuel) — the object remembers its own state between method calls.

5. Instance Attributes vs Class Attributes

An instance attribute belongs to one specific object (set with self.something, usually inside __init__). A class attribute belongs to the class itself, and is shared by every object created from it.

class Student:
    school = "UoB"          # class attribute — shared by all students

    def __init__(self, name):
        self.name = name     # instance attribute — unique per student

a = Student("Ali")
b = Student("Sara")

print(a.school, b.school)   # UoB UoB
print(a.name, b.name)       # Ali Sara
Rule of thumb: If every object should start with the exact same value, and that value rarely changes, a class attribute usually fits. If the value is unique to each object, it belongs on self as an instance attribute.

6. Encapsulation

Encapsulation means bundling data and the methods that work on that data together inside one object, and controlling how that data is accessed or changed from the outside — instead of letting any part of the program modify it freely.

class BankAccount:
    def __init__(self, balance):
        self._balance = balance   # "protected" by convention (single underscore)

    def deposit(self, amount):
        if amount > 0:
            self._balance += amount

    def get_balance(self):
        return self._balance

account = BankAccount(1000)
account.deposit(500)
print(account.get_balance())  # 1500
Why this matters: Instead of changing account._balance directly from anywhere in the program, changes go through deposit(), which can enforce rules — like refusing a negative deposit. Python doesn't strictly block direct access; the underscore is a signal to other programmers: "treat this as internal."

7. Inheritance

Inheritance lets one class (the child) reuse the attributes and methods of another class (the parent), instead of rewriting the same code again. The child can also add new behavior or change existing behavior.

class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound."

class Cat(Animal):          # Cat inherits from Animal
    def speak(self):
        return f"{self.name} says Meow!"

class Fish(Animal):
    pass   # Fish doesn't override speak() — it uses Animal's version

cat = Cat("Whiskers")
fish = Fish("Nemo")

print(cat.speak())    # Whiskers says Meow!
print(fish.speak())   # Nemo makes a sound.

Fish got a working speak() method for free, just by inheriting from Animal — it never had to define one itself.

8. Method Overriding and super()

A child class can override a parent's method by defining a method with the same name — Python will use the child's version instead. super() lets the child still call the parent's original version when it's useful, rather than replacing it completely.

class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

class Manager(Employee):
    def __init__(self, name, salary, team_size):
        super().__init__(name, salary)   # reuse Employee's setup
        self.team_size = team_size

m = Manager("Ayesha", 90000, 5)
print(m.name, m.salary, m.team_size)  # Ayesha 90000 5
Notice: Manager didn't need to repeat self.name = name and self.salary = salary — super().__init__() handed that work off to Employee, and Manager only added what was new: team_size.

9. Polymorphism

Polymorphism means objects of different classes can respond to the same method call, each in their own way. The calling code doesn't need to know exactly which class it's dealing with — it just calls the method and trusts each object to handle it correctly.

class Cat:
    def speak(self):
        return "Meow!"

class Dog:
    def speak(self):
        return "Woof!"

class Duck:
    def speak(self):
        return "Quack!"

animals = [Cat(), Dog(), Duck()]

for animal in animals:
    print(animal.speak())
Output:Meow! Woof! Quack!

The loop calls .speak() the exact same way on every object, but each class provides its own version of what that means.

10. Abstraction

Abstraction means exposing only the necessary details of how something works, while hiding the complicated logic behind a simple method call. As a user of an object, you usually only need to know what a method does, not how it does it internally.

class CoffeeMachine:
    def make_coffee(self):
        self._heat_water()
        self._grind_beans()
        self._brew()
        return "Coffee is ready!"

    def _heat_water(self):
        pass  # internal detail

    def _grind_beans(self):
        pass  # internal detail

    def _brew(self):
        pass  # internal detail

machine = CoffeeMachine()
print(machine.make_coffee())

Whoever uses CoffeeMachine only needs to call make_coffee() — they don't need to know or worry about how heating, grinding, or brewing actually happen underneath.

11. Dunder Methods: Customizing Built-in Behavior

Python objects can define special "dunder" (double-underscore) methods that let them work with built-in functions and operators in a customized way. __init__ is one example; __str__ and __repr__ are two more you'll see constantly.

class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def __str__(self):
        return f"{self.name} — ${self.price}"

item = Product("Laptop", 1200)
print(item)          # Laptop — $1200 (uses __str__ automatically)
Without __str__: print(item) would instead show something unhelpful like <__main__.Product object at 0x7f...>. Defining __str__ tells Python exactly how the object should describe itself when printed.

12. The Four Pillars: Quick Recap

Pillar Idea Example from above
Encapsulation Bundle data + behavior, control access BankAccount with deposit()
Inheritance Reuse a parent class's data/behavior Cat(Animal)
Polymorphism Same method call, different behavior per class animal.speak()
Abstraction Hide internal complexity behind a simple interface machine.make_coffee()

13. OOP vs Procedural: Quick Comparison

Procedural (functions + data separate) Object-Oriented (bundled together)
Data passed around between standalone functions Data lives inside objects alongside the methods that use it
Harder to model many similar "things" cleanly A class describes the shape once; many objects reuse it
Natural for short scripts and simple, linear tasks Natural for larger programs with many related, stateful things
Quick gut-check: Ask "am I going to need many similar things, each with their own data and shared behavior?" If yes, a class usually fits well. If it's a one-off calculation or simple linear script, plain functions are often simpler.

14. Common Mistakes

  • Forgetting self: Leaving self out of a method's parameters causes an error, since Python always passes the object automatically as the first argument.
  • Confusing the class with an object: Dog is the blueprint; Dog() creates an actual object. Trying to use the class itself as if it already had data will fail.
  • Modifying a class attribute expecting it to be per-object: If a mutable class attribute (like a list) is changed through one object, every object sharing that class attribute is affected too.
  • Forgetting super().__init__(): A child class that defines its own __init__ without calling super().__init__() may lose the setup work the parent class was supposed to do.
  • Overriding a method but breaking its expected behavior: Other code calling that method may assume it still behaves the way the parent's version did.

15. OOP + Everything Else: The Connections

OOP doesn't replace the earlier topics — it often builds on top of them. A class's methods can use conditionals, loops, dictionaries as attributes, and even closures and decorators.

class Cache:
    def __init__(self):
        self._data = {}          # a dictionary stored as an attribute

    def get_or_compute(self, key, compute_fn):
        if key not in self._data:
            self._data[key] = compute_fn()
        return self._data[key]
Notice: @staticmethod, @classmethod, and @property — covered in the decorators handout — are themselves decorators specifically designed to work with classes.

16. Where OOP Is Actually Used

Not just a classroom exercise — almost every substantial piece of software leans on OOP somewhere. Here's where you'll actually run into it.

🎮 Game Development

A character, an enemy, a weapon, a power-up — each is naturally modeled as a class, with its own attributes (health, position, speed) and methods (move, attack, take damage).

🌐 Web Frameworks

Django models represent database tables as classes. FastAPI and Flask often organize request handlers, database sessions, and services as classes with their own state and methods.

📱 GUI and Mobile Apps

Buttons, windows, screens, and widgets are almost always represented as objects — each button knows its own label, position, and what to do when clicked.

🤖 AI / Machine Learning

A model, a layer, a dataset loader, or a training pipeline is commonly built as a class — for example, PyTorch's nn.Module is a class that every neural network layer or model inherits from.

🗄️ Databases and ORMs

Object-Relational Mappers (ORMs) represent each database table as a class and each row as an object, so code can work with user.name instead of raw SQL rows.

🧩 Large Codebases in General

Any system with many related "things" that share behavior but carry their own data — users, orders, sensors, documents — tends to reach for classes to keep that structure organized as the codebase grows.

17. OOP at Real Companies

These are well-known, publicly documented examples of the same OOP ideas from this handout, used at scale.

🎮 Unity & Unreal Engine — Game Objects

Both engines (used by countless game studios) are built around the idea that everything in a game — characters, cameras, lights, obstacles — is an object with attributes and behavior, often organized through class inheritance and components.

🐍 Django (used by Instagram, Pinterest, Mozilla)

Django's model layer represents every database table as a Python class, with each row becoming an object — the same class/object idea from this handout, powering real production databases.

🔥 PyTorch (developed at Meta / Facebook AI)

Every neural network in PyTorch is written as a class inheriting from nn.Module, with layers as attributes and the forward pass as a method — inheritance and encapsulation applied directly to AI model-building.

☕ Java at Large Enterprises (banks, airlines, telecoms)

Java, one of the most widely used enterprise languages, is built entirely around classes and objects — modeling customers, accounts, transactions, and flights as objects is standard practice across huge, long-running systems.

🍎 Apple — UIKit / SwiftUI

iOS app development represents every screen element — buttons, labels, views — as an object, with inheritance used heavily to share common behavior across different kinds of UI components.

Takeaway: None of these companies invented a special kind of OOP — they're all organizing large amounts of related data and behavior using the exact same class/object pattern practiced in this handout, just at a much bigger scale.

One-Minute Summary

  • OOP organizes a program around objects that bundle data (attributes) and behavior (methods) together.
  • A class is a blueprint; an object is a real instance built from that blueprint. self keeps each object's data separate.
  • Encapsulation: bundle data with the methods that work on it, and control access to it.
  • Inheritance: a child class reuses (and can extend or override) a parent class's behavior; super() calls the parent's version.
  • Polymorphism: different classes can respond to the same method call, each in their own way.
  • Abstraction: hide internal complexity behind a simple method the user can call.
  • Instance attributes belong to one object; class attributes are shared by every object of that class.
  • OOP shows up in game development, web frameworks, GUIs, ORMs, and AI model-building (like PyTorch's nn.Module).
Mental model: OOP = describe a "thing" once as a class, then create as many independent objects from it as you need, each remembering its own data.
