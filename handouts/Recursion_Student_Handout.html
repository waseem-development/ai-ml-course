Recursion

Student Handout
From a function calling itself to real-world problems that are naturally recursive

1. What is Recursion?

Recursion is when a function solves a problem by calling itself on a smaller version of the same problem, until the problem becomes so small that the answer is obvious.

Easy mental model: Recursion = solving a big problem by solving a smaller copy of the same problem, and trusting that smaller copy to work. 
def countdown(n):
    if n == 0:
        print("Liftoff!")
    else:
        print(n)
        countdown(n - 1)

countdown(3)
Output:3 2 1 Liftoff!

2. The Three Things Every Recursive Function Needs

Every recursive function is built from three ingredients. Miss any one of them and the function either breaks or never stops.

1. Base Case (the starting point)

The simplest version of the problem, small enough to answer directly, with no further recursive call. This is the "bottom" that everything else builds up from.

2. Logic (the actual work)

What the function does at each step — the calculation, comparison, or action performed before (or after) it calls itself again.

3. Terminating Condition (how to stop)

The condition that checks whether the base case has been reached, so the function knows when to stop calling itself instead of continuing forever.

def countdown(n):
    if n == 0:            # base case
        print("Liftoff!")
    else:                 # terminating condition (n == 0 not yet reached)
        print(n)          # logic
        countdown(n - 1)  # smaller problem
⚠️ Miss the terminating condition: The function keeps calling itself with no way to stop — this is called infinite recursion. Python eventually raises a RecursionError: maximum recursion depth exceeded, but by then the program has already gone badly wrong.

3. Why Do We Need Recursion?

Almost anything recursion can do, a loop can also do. So why bother?

  • Some problems are naturally recursive. A folder contains files and other folders, which contain files and other folders. A family tree, a chapter that contains sections that contain sub-sections — these structures are already defined in terms of smaller copies of themselves.
  • Cleaner code for branching problems. When a problem can split into multiple smaller problems (like exploring both left and right paths in a maze), a loop needs extra bookkeeping (stacks, queues) to keep track of where it's been. Recursion gets this "for free" using the call stack.
  • Matches how we already think about the problem. "To sort this list, sort the left half, sort the right half, then merge them" reads almost like a definition, and recursion lets you write code that mirrors that definition directly.
  • Some data structures are defined recursively. Trees and linked lists are usually defined as "a node, plus more of the same structure." Writing functions that walk them often reads more naturally as recursion than as a loop.
In short: Recursion isn't about being "fancy" — it's the natural way to describe problems that are made of smaller copies of themselves.

4. A Simple Example: Factorial

The factorial of a number is defined in terms of a smaller factorial — a textbook example of a recursive definition.

def factorial(n):
    if n == 0:                  # base case
        return 1
    return n * factorial(n - 1)  # recursive case

print(factorial(5))  # 120

Notice how closely the code matches the math definition: 5! = 5 * 4!, 4! = 4 * 3!, and so on, until 0! = 1.

5. Tracing a Recursive Call

Every time a function calls itself, Python remembers where it needs to "come back to" using something called the call stack. Tracing factorial(3) step by step:

→factorial(3) calls factorial(2), waiting to multiply by 3
→factorial(2) calls factorial(1), waiting to multiply by 2
→factorial(1) calls factorial(0), waiting to multiply by 1
→factorial(0) hits the base case, returns 1
←factorial(1) returns 1 * 1 = 1
←factorial(2) returns 2 * 1 = 2
←factorial(3) returns 3 * 2 = 6
Key idea: Calls go "down" until the base case is hit, then answers come back "up," each call finishing the work it was waiting on.

6. Recursion vs Iteration

Anything written with recursion can usually also be written with a loop. Neither is "better" in general — it depends on how naturally the problem fits.

Iteration (loop)Recursion
Repeats using for / whileRepeats by calling itself
Keeps state in variables you manageKeeps state in each function call's own local variables
Natural for simple counting/repetitionNatural for branching or nested structures
# Iterative factorial
def factorial_iterative(n):
    result = 1
    for i in range(1, n + 1):
        result *= i
    return result

Same answer as the recursive version — just a different way of expressing the repetition.

✅ When to Reach for Recursion

  • The data itself is nested or branching — folders inside folders, a tree, a linked list, nested JSON. The structure already "contains smaller copies of itself," so recursive code tends to read very close to the problem description.
  • The problem naturally splits into smaller sub-problems — divide-and-conquer tasks like merge sort, or "solve the left half, solve the right half, combine."
  • You need to explore multiple paths and backtrack — mazes, puzzles, generating combinations — where a loop would need extra manual bookkeeping (a stack or queue) to keep track of where it's been.
  • The definition is already recursive — factorial, Fibonacci, GCD — so the code mirrors the math almost exactly, which makes it easier to read and trust.

🚫 When to Avoid Recursion

  • Simple counting or straightforward repetition — looping over a list, counting up to a number, repeating an action a fixed number of times. A for loop says the same thing more directly, with less overhead of tracking calls.
  • Very deep or unbounded repetition. Python limits how many calls can be waiting on the call stack at once. Recurse too deeply (for example, processing a very long list one item at a time) and you'll hit a RecursionError: maximum recursion depth exceeded. A loop has no such limit.
  • When it hurts readability instead of helping it. If you find yourself fighting to express something recursively that a two-line loop would say clearly, that's a sign the problem isn't actually recursive in nature — it's just being forced into that shape.
  • When you need to closely track state as it changes. Loops keep everything in variables you can inspect at any point. Recursion spreads state across many nested calls, which can be harder to step through while debugging.
Quick gut-check: Ask "does solving this problem require solving a smaller version of the exact same problem?" If yes, recursion usually fits well. If you're just repeating the same fixed action a number of times, reach for a loop instead.

7. A Practical Example: Sum of a List

def sum_list(numbers):
    if not numbers:            # base case: empty list
        return 0
    return numbers[0] + sum_list(numbers[1:])  # first item + rest

print(sum_list([1, 2, 3, 4]))  # 10

The problem "sum this list" is broken into "add the first item to the sum of everything else" — a smaller version of the same problem.

8. A Practical Example: Reversing a String

def reverse_string(text):
    if len(text) <= 1:               # base case
        return text
    return reverse_string(text[1:]) + text[0]

print(reverse_string("hello"))  # "olleh"

9. Multiple Recursive Calls: Fibonacci

Some functions call themselves more than once. The Fibonacci sequence is defined as each number being the sum of the two before it.

def fibonacci(n):
    if n <= 1:                                # base case
        return n
    return fibonacci(n - 1) + fibonacci(n - 2) # two recursive calls

print(fibonacci(6))  # 8
Notice: Each call branches into two more calls, forming a tree of calls rather than a single straight line. This pattern is called tree recursion.

Dry Run: fibonacci(4)

Every call keeps branching into two smaller calls until it hits a base case (n <= 1), then the results add back up.

→fibonacci(4) needs fibonacci(3) + fibonacci(2)
→fibonacci(3) needs fibonacci(2) + fibonacci(1)
→fibonacci(2) needs fibonacci(1) + fibonacci(0)
→fibonacci(1) → base case → returns 1
→fibonacci(0) → base case → returns 0
←fibonacci(2) = 1 + 0 = 1
→fibonacci(1) → base case → returns 1
←fibonacci(3) = 1 + 1 = 2
→fibonacci(2) needs fibonacci(1) + fibonacci(0)
→fibonacci(1) → base case → returns 1
→fibonacci(0) → base case → returns 0
←fibonacci(2) = 1 + 0 = 1
←fibonacci(4) = 2 + 1 = 3
Notice: fibonacci(2) and fibonacci(1) each get computed more than once here — a side effect of tree recursion worth being aware of, even without worrying about how "expensive" it is.

10. Mutual Recursion

Two functions can call each other instead of calling themselves directly. This is called mutual recursion.

def is_even(n):
    if n == 0:
        return True
    return is_odd(n - 1)

def is_odd(n):
    if n == 0:
        return False
    return is_even(n - 1)

print(is_even(4))  # True

11. Common Mistakes

  • Forgetting the base case: The function calls itself forever, and Python eventually raises a RecursionError.
  • Base case that's never actually reached: For example, decreasing by 2 each time but checking for exactly 0 when starting from an odd number.
  • Forgetting to return the recursive call: Calling the function again but not using its result means the answer is silently lost.
  • Not shrinking the problem: If each call doesn't move closer to the base case, the recursion never ends.
  • Mixing up "return" and "print": Printing inside a recursive call shows progress, but the function should usually still return a value to the caller.

12. Recursion + The Call Stack: The Connection

Every function call — recursive or not — gets placed on the call stack, a structure that keeps track of "what to do next" once the current call finishes. In recursion, this happens over and over, which is why tracing a recursive function often looks like a stack of waiting calls, each one paused until the one below it finishes.

Mental picture: Imagine a stack of plates. Each recursive call adds a plate. Once the base case is hit, plates are removed one at a time, each one completing its leftover work as it comes off.

13. Where Recursion Is Actually Used

Not just a classroom exercise — recursion shows up constantly in real software. Here's where you'll actually run into it.

📁 File Systems

Every folder can contain more folders, which can contain more folders. When you "search this folder and everything inside it" — like Windows Explorer's search, or the find command on Linux — the underlying code is almost always recursive: check this folder, then recurse into every subfolder it contains.

🌳 Trees

The webpage you're reading right now is a tree of nested HTML elements. A browser rendering a page, a company's org chart, a decision tree in a game AI, a file explorer's folder tree — all of these are walked recursively, because a tree is naturally "a node, plus more trees underneath it."

🔗 Linked Lists

A linked list node points to the next node, which points to the next — the same shape as a recursive definition. Many linked-list operations (searching, reversing, printing) are written recursively for exactly this reason.

{ } Parsing Nested Data

JSON, XML, math expressions, and even programming languages themselves are nested: a JSON object can contain another JSON object inside it. Parsers and interpreters — including the one running this Python code — rely heavily on recursion to handle that nesting correctly.

🔀 Divide-and-Conquer Algorithms

Algorithms like merge sort and quick sort work by splitting a list into smaller pieces, sorting each piece the same way, then combining the results. That "solve the smaller piece the same way" step is recursion.

🧩 Backtracking & Puzzles

Solving a maze, filling in a Sudoku grid, or generating every possible combination of a set of items usually works by trying a choice, recursing to see if it leads to a solution, and backing out if it doesn't. Chess engines exploring possible moves work the same way.

➗ Mathematical Definitions

Factorial, Fibonacci, powers, and the greatest common divisor are all defined recursively in math itself — so the code ends up looking almost identical to the definition you'd write on paper.

14. Recursion at Real Companies

These are well-known, publicly documented examples of the same recursive ideas from this handout, used at scale.

🌐 Google — Web Crawling

Search engines discover the web by starting at a page, following its links, then following the links on those pages, and so on — the same "look at this node, then recurse into what it points to" pattern as walking a tree or a linked list.

🧭 Chrome & Firefox — Rendering Web Pages

Browsers built by Google (Chrome) and Mozilla (Firefox) render a page by walking the DOM tree — the nested structure of HTML elements — recursively: draw this element, then recurse into each of its children.

🐙 GitHub / Git — Version Control

Git stores a project's history as a tree of commits and a tree of directories/files at each commit. Operations like computing a diff across nested folders, or walking commit history, are naturally recursive tree walks.

🛠️ Compiler & Language Teams (LLVM/Clang at Apple, GCC, Python's own CPython interpreter)

Source code is inherently nested — an if inside a function inside a class inside a module. Compilers and interpreters parse and evaluate that nested structure using recursive functions, often called a "recursive descent parser."

📄 Adobe — PDF & Document Rendering

PDFs can contain nested layout elements (pages, frames, groups of objects within groups). Rendering engines walk this nested structure recursively to draw the final page.

🗺️ Games & AI (chess engines, pathfinding in games like those from Ubisoft/EA)

Chess and strategy-game AI explore possible future moves by recursively trying a move, imagining the opponent's reply, trying the next move, and so on — the same backtracking pattern used for solving mazes and puzzles.

🗄️ Database Systems (used by companies like Oracle, PostgreSQL contributors, MongoDB)

Some SQL databases support "recursive queries" (e.g. WITH RECURSIVE in PostgreSQL) specifically to handle naturally recursive data, like an employee table where each employee has a manager who is also an employee.

Takeaway: None of these companies invented a special kind of recursion — they're solving the exact same "problem made of smaller copies of itself" pattern you just practiced, just at a much bigger scale.

One-Minute Summary

  • Recursion = a function that solves a problem by calling itself on a smaller version of that problem.
  • Every recursive function needs a base case (stops the recursion) and a recursive case (shrinks the problem).
  • Recursion is useful because some problems and data structures — folders, trees, nested lists — are naturally defined in terms of smaller copies of themselves.
  • Recursive calls are tracked using the call stack: calls go "down" to the base case, then results come back "up."
  • A function can call itself once, call itself multiple times (tree recursion), or call another function that calls it back (mutual recursion).
  • Common mistakes: missing base case, base case never reached, forgetting to return the recursive result, or not shrinking the problem.
  • You'll see recursion in file systems, trees, linked lists, parsing, sorting algorithms, and backtracking.
Mental model: Recursion = trust that a smaller version of the same problem will solve itself, then use that answer to solve the bigger one.
